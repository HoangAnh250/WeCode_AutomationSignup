# Weverse account-creation adapter

Production startup now uses createProductionEngine, which registers WeverseAdapter with key create-account. The generic createEngine still has an empty registry unless one is passed; existing fixture/missing-adapter tests retain that contract.

## Files and boundaries

- automation/WeverseAdapter.ts: identity, OTP, consent, mutation gate, confirmed-result recovery and session decision.
- automation/weverse/WeversePage.ts: English controls evidenced by the captured frontend: Sign up with email, Email, Password, Confirm new password, Username, Send Verification Code, Verify Code, Next, consent checkboxes, Sign up now and Start.
- automation/weverse/protocol.ts: exact origin/method/path response matching and HAR-shaped response validation.
- automation/weverse/state.ts and repositories/workflow-state.repository.ts: encrypted draft and result journal, guarded by the current task/run lease.
- automation/production-engine.ts: production dependency injection and explicit registry registration.

The adapter uses the BrowserManager-owned page/context and the engine-bound EmailVerificationCoordinator. It returns a result to WorkerExecutor; only AccountManager persists the successful account and marks CREATED. One account is supported per task run.

## HAR mapping

The source is D:/Deepseek/signup.har (815 entries); it is not copied into the repository. Account API requests #358, #407, #410, #608, #628, #631, #637 and #675 establish service configuration, OTP session/dispatch, verification grant, nickname validation, terms, signup and token validation. The account route uses redirect_method=COOKIE, as captured. Service/device headers and cookies are generated by the current frontend, never copied from the HAR. Suggestion/timezone/assets/preflights run naturally in the page. Gmail web traffic is replaced by IMAP; noreply@weverse.io appeared in the captured Gmail responses and remains configurable using WEVERSE_OTP_SENDER.

## Persistence and retry

Apply migration 202611110001_workflow_state. workflow_states contains one encrypted state per task and a unique email reservation. The state holds the generated password, remote OTP session/grant and minimal confirmed-user evidence. Public checkpoints contain stage and verification references, not these secrets. Identity policy changes reset an unconfirmed draft; otherwise retries keep the same identity. Unknown or created outcomes are never resubmitted.

A recreated browser form obtains a fresh remote OTP session and fresh verification tracking; a code from an earlier remote session is not reused. Tracking exists before dispatch and its expiry is clamped to the remote receipt. Checkpoint patches merge under a row lock and update the execution's in-memory view.

The final UI-generated request is intercepted, correlated to identity/auth grant and the current Agree to All consent documents, and fenced with beforeExternalMutation. Forwarding uses route.fetch with maxRetries=0 and maxRedirects=0, preserving the BrowserContext proxy and cookies. This avoids Chromium transport-level POST replay after an empty response. It does not claim remote exactly-once semantics. Duplicate frontend submissions are aborted. Service workers are blocked so the context mutation gate cannot be bypassed by a previously installed worker.

The confirmed response is journaled before fulfilling it to the frontend. If callback/authentication/session storage or a cooperative pause subsequently fails, WorkerExecutor can persist the confirmed account through AccountManager without another signup. Losing the response before confirmation leaves UNKNOWN and requires reconciliation. Process-crash/manual reconciliation administration is not implemented by this adapter; there is no automatic reset of UNKNOWN.

The operator requested Agree to All. The adapter uses the aggregate checkbox, including required and optional signup terms; the final request must contain agreed=true for every current document. Document IDs come from the current response. Unexpected or ambiguous controls and mismatched payloads stop execution. A challenge/rate-limit is reported; no challenge solving, proxy-based restriction bypass or hidden replay is implemented.

Session snapshots are saved only after correlated token validation; an unconfirmed session does not erase a created account. The account's verified status means email OTP and account creation were confirmed, not a guarantee of future token validity. Existing-account session reuse for signup is deliberately unsupported; validateSession returns false. storageState does not guarantee sessionStorage portability or remote session refresh.

## Running

1. npm run db:generate
2. npm run db:migrate
3. npm run backend:build
4. Restart the API/worker using the current backend. npm run backend:worker starts the registered production engine.

Start WeCode.cmd applies migrations when bringing stopped local services up. An already-running older worker is not replaced automatically. Worker startup fails clearly if workflow_states is unavailable. Set task count to 1. Password policy must include letters/numbers/symbols and length must not exceed the captured 32-character limit. English is the implemented UI locale. Optional config.weverse.timeZone is validated against the final payload; otherwise the site's default selection is retained.

## Verification and limits

Local Chromium tests exercise UI -> HAR-shaped local API -> real OTP coordinator -> WorkerExecutor -> AccountManager (database port fixture), encrypted draft round-trips, current-lease rejection, production registration, missing-agreement tampering, duplicate submissions, authenticated proxy forwarding, lost signup response and confirmed-result recovery. They do not create real Weverse accounts or connect to a live Gmail inbox.

The selectors and protocol were derived from the provided capture. Current live Weverse behavior, provider restrictions, real forwarding and restored authentication still require operator validation. PostgreSQL/Redis integration depends on Docker/local services and must be distinguished from fixture evidence. No HAR credentials, tokens or personal mailbox values are embedded in this adapter.

## Read-only live entry check

A fresh isolated Chromium browser reached the current live /en/signup/credential page after refusing optional cookie consent and following the site's return to /en/login -> Sign Up -> email signup entry. The current accessible labels include a required suffix (Emailrequired, Passwordrequired, Confirm Passwordrequired, Usernamerequired); selectors support that suffix. Password placeholders currently say Enter Password for both password fields, so the adapter distinguishes them using labels. The check did not enter an identity, request an OTP or create an account. OTP, consent and final-submission controls remain verified against HAR-derived fixtures rather than a live signup.

The default sender value is evidence from Gmail web response text, not a guarantee of the sender of every future message. IMAP still requires matching the original forwarded recipient and time window. Existing-account login, CAPTCHA handling and arbitrary site-origin overrides are outside the adapter.

## Operator controls update

The adapter unchecks Block Overseas Logins and the final mutation gate requires blockOverseasSignin=false. Browser visibility is configured per task through browser.headless. The desktop batch endpoint creates individual count=1 rows; the engine still owns exactly one account per run. OTP extraction removes tracking URLs before deciding whether visible codes are ambiguous. See ../../../docs/OTP_BATCH_FIX.md.

## Collapsed consent groups correction (0.1.6)

After OTP verification and Next, the adapter uses the visible Agree to All checkbox. It no longer tries to select hidden child terms individually. Browser fixtures reproduce collapsed children and a disabled submit button that becomes enabled only when the aggregate control is selected. The final mutation gate requires every current document's agreement to be true. Block Overseas Logins remains independently enforced as false. Privacy cookie consent at entry remains Refuse and continue and is separate from signup terms.

Older selector/consent failures are eligible for manual retry only with outcome NOT_CREATED. Automatic retry is unchanged, and UNKNOWN/CREATED remain protected.
